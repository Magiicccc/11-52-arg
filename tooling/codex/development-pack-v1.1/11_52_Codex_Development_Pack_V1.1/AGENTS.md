# AGENTS.md — 《11:52》仓库最高实施规则

## 0. 工作语言与交付

- 代码标识、文件名和 Schema 字段使用英文；产品文案与文档使用简体中文。
- 每次任务只处理一个可验证的工作单元。不得在同一任务中同时重构引擎、改剧情、换 UI 和新增 App。
- 任务结束必须说明：改了什么、运行了什么验证、仍有哪些明确缺口。

## 1. 权威顺序

发生冲突时按以下顺序裁决：

1. 当前任务中用户的明确新指令；
2. `docs/authority/FROZEN_DECISIONS.md`；
3. 第一册 World Bible；
4. 第二册 Narrative Bible；
5. 第三册 Systems Bible；
6. 第四册 Content Bible；
7. 第五册 UI / Art Bible；
8. `references/ui/11_52_UI_Reference_Pack_V1.0_全量版/`中的原始截图、manifest与状态矩阵；
9. 第六册 Codex Development Bible、`PLAN.md`与本任务提示；
10. 临时搜索结果与实现推测。

视觉冲突时，原始参考包优先于 Word 中的缩略图。剧情冲突时，World Bible 与 Narrative Bible 优先。不要用“现实修正”解释代码或内容漏洞。

## 2. 禁止擅自创作的内容

除非当前任务明确授权，不得新增或修改：

- 世界真相、错层规则、身份锚点规则；
- 沈川、玩家、潘博文、陈屿、周岚、旧雨17的关系和动机；
- 日期、密码 `230917`、场景 ID、结局条件；
- 正式聊天、帖子、新闻、备忘录、音视频台词；
- 谜题答案、证据依赖、修正周目规则；
- App 导航结构与现实品牌页面语法。

发现缺口时：使用显式 `TODO-CONTENT` 或 `REFERENCE-GAP`，记录到对应缺口文档；不得以自创内容掩盖缺口。

## 3. 视觉实施门禁

- 不得凭记忆设计“像 iPhone”“像微信”“像小红书”的通用界面。
- 实现任何正式页面前，读取该 App 的：
  - `manifest.json`
  - `source-log.md`
  - `state-matrix.md`
  - `implementation-contract.md`
  - `measurements.json`
  - `raw/`与`annotated/`
- 页面状态只能采用 `direct_real`、`derived_real` 或 `system_inherited` 三种已冻结来源。
- 先用中性占位内容完成 DOM/CSS 复刻和 Playwright 对比；视觉通过后才注入剧情内容。
- 不得把整张截图作为不可交互背景。
- 真实 App 图标使用冻结资源；不得以 Emoji、近似手绘图标或通用占位图标替代。
- 目标主视口为 `402x874`，附加回归视口为 `440x956`。

## 4. 工程基线

- React + TypeScript strict + Vite。
- DOM/CSS 实现，不使用 Canvas 游戏引擎。
- 正式状态持久化使用 IndexedDB；localStorage 只允许保存非关键偏好或迁移标记。
- 运行时 Schema 校验使用 Zod 或等价方案；内容包不得绕过验证直接进入游戏。
- 单元与模型测试使用 Vitest；端到端与视觉测试使用 Playwright。
- 首个版本为纯前端、本地存档；不得把服务器、实时大模型或第三方真实账号作为主线依赖。
- 依赖使用当前稳定版本初始化，并提交锁文件。禁止无理由升级依赖。

## 5. 唯一状态源

- `GameState`是剧情状态唯一事实源。
- UI 组件不得保存无法由 `GameState`、事件日志或内容包重建的隐藏剧情状态。
- 所有关键玩家行为必须归一化为 `StoryEvent`。
- 所有剧情变化必须由 Trigger + Condition + Action 事务产生。
- 不得在 React 组件中用散落的 `setTimeout`、布尔变量或硬编码页面判断推进主线。

## 6. 事件与来源

- 事件命名采用 `<domain>.<entity>.<verb>`，例如 `photo.item.inspected`。
- 每次世界响应必须标注来源：
  - `H`：人物主动行为；
  - `A`：沈川预设自动程序；
  - `P`：潘博文异常接口；
  - `C`：现实修正副作用。
- NPC 只能根据自己的知识状态与已接收材料回应。不得让 NPC 凭空知道玩家点击了什么。
- 微延迟只用于表演，不得成为主线等待条件。
- 关键事务必须幂等；刷新、返回和重复进入不得重复扣除身份锚点或重复发消息。

## 7. 内容与 App 规则

- 所有可见 App 必须可以打开并产生合理反馈。
- A 级 App：完整搜索、输入、播放、分享、状态变化和端到端测试。
- B 级 App：列表、详情、至少一种用户操作、历史或收藏。
- C 级 App：至少一种真实可用功能与可信内容；不得空白或只显示“暂未开放”。
- 开局可见内容中普通生活内容不少于约 65%。
- 普通内容可以没有谜题答案，但每条正式内容必须具有至少一个冻结叙事功能；“填满列表”“增加真实感”不能作为唯一功能。
- 每个 `ContentItem` 必须填写 `NarrativeMetadata`，并连接至少一个世界事实、人物特征、关系节拍或跨App连续性节点。
- 核心人物必须拥有独立于潘博文调查的生活线；早期主要联系人至少一半可见交流不谈案件。
- 不得使用随机生成的朋友圈、评论、聊天、订单或浏览历史作为正式内容。
- 有意义不等于处处藏谜；`clueRole: none` 是正常且应占多数的状态。
- 同一线索跨 App 出现时，必须保持日期、金额、地点、人物和来源链一致。
- 同一源文件的多个副本不能被计为多个独立见证。

## 8. 媒体资产

- 人物与地点必须使用固定参考包。
- 先制作正常母图；R0—R5变体从同一母图局部编辑，不得重新随机生成整张图。
- AI偶然瑕疵不能被升级为剧情线索。
- 每个媒体资产必须有 `MediaAssetManifest`、来源链和 QA 状态。
- 图片、音频或视频加载失败时，主线必须有剧情内降级路径。

## 9. 存档、周目与迁移

- 存档包含快照、追加式事件日志、一次性触发凭据、内容包版本与迁移记录。
- 任何 Schema 变更必须新增迁移，不得直接破坏旧存档。
- 坏结局周目通过显式 `RunPatch`加载，不得静默覆盖完整档案。
- 必须提供完整重置和档案回看能力。

## 10. 测试要求

每个实施任务至少运行与范围对应的：

- `typecheck`
- 单元/模型测试
- Playwright主路径测试
- 目标页面视觉快照
- 刷新恢复测试

核心合并门禁：

- 无 TypeScript 错误；
- 无内容 Schema 错误；
- 无叙事语义错误；孤儿内容数量为0；
- 无重复触发；
- 无强制谜题死路；
- 双手机同步事务完整；
- 所有本任务页面可返回、可刷新恢复；
- 视觉差异无未解释的重大偏差；
- 没有未标记的占位内容。

## 11. 任务边界与变更控制

- 修改冻结剧情或内容前，先更新 `docs/authority/CHANGE_REQUEST.md`，说明原因、影响册次、受影响场景、迁移和测试。
- 无批准时，继续完成不冲突部分，并把冲突记录到 `docs/authority/CONFLICT_REPORT.md`。
- 不得为“代码更方便”而改变正史。
- 不得为了快速通过测试而删除断言、跳过场景或把异常状态写死。

## 12. 完成定义

一个页面或系统只有在以下条件同时满足时才算完成：

1. 使用冻结数据合同；
2. 可交互，不是图片背景；
3. 可从正确路径进入和退出；
4. 刷新后状态正确；
5. 关键行为产生规范事件；
6. 视觉通过参考包对照；
7. 自动测试通过；
8. 无未记录的逻辑或参考缺口；
9. 内容具有明确叙事功能，不存在随机填充或无语义孤儿项。
